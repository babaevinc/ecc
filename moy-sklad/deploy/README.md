# Свой сервер для «Моего склада»

Сервер арендуется в российском облаке (решение B из `docs/adr/0002-data-residency.md`): на нём работает
официальный Supabase для самостоятельного размещения, данные остаются в России.

| Файл | Что делает |
|---|---|
| `install.sh` | Один раз готовит сервер: обновления, файрвол, Supabase закреплённой версии (`self-hosted/v0.8.3`), HTTPS, закрытая регистрация, ежедневные копии |
| `docker-compose.moysklad.yml` | Закрывает базу данных от интернета: Docker обходит ufw, а официальная настройка открывает порт 5432 всем |
| `migrate.sh` | Применяет новые миграции (каждую целиком или никак), ставит функцию `notify` и ежеминутную отправку push |
| `create-owner.sh` | Создаёт компанию, аккаунт владельца и первый склад. Пароль вводится на сервере |
| `backup.sh` | Ежедневная копия базы и ключей сервера, проверка, что копия читается, хранение 14 дней |

## 1. Арендуйте сервер

У любого российского облака (Timeweb Cloud, Selectel, Yandex Cloud и др.) создайте виртуальный сервер:

- **Ubuntu 24.04**, регион в России;
- **2 vCPU, 4 ГБ памяти** — минимум для Supabase; 8 ГБ — с запасом;
- **диск SSD 40–60 ГБ**;
- в настройках сети (группа безопасности, файрвол облака) разрешите входящие **22, 80, 443 (TCP) и 443 (UDP)**,
  остальное закройте.

Цену смотрите в прайсе провайдера на день заказа.

При создании сервера добавьте SSH-ключ. На Windows в PowerShell:

```powershell
ssh-keygen -t ed25519 -C "moy-sklad-deploy" -f $HOME\.ssh\moy-sklad-deploy
```

Пароль к ключу оставьте пустым: этим ключом будет входить GitHub. В панель провайдера вставьте содержимое
файла `moy-sklad-deploy.pub` (открытая часть). Файл без `.pub` — закрытый ключ: никому его не отправляйте.

## 2. Домен

Нужен домен или поддомен, например `sklad.ваша-компания.ru`. У регистратора домена создайте **A-запись**
на IP сервера. Сертификат HTTPS сервер получит сам (Let's Encrypt), когда запись заработает — обычно
в течение часа.

## 3. Секреты в GitHub

**Settings → Environments → production → Environment secrets** (окружение с обязательным утверждением,
см. `docs/WINDOWS-SETUP.md`, раздел 10):

| Секрет | Значение |
|---|---|
| `DEPLOY_HOST` | IP сервера |
| `DEPLOY_SSH_KEY` | Всё содержимое файла `moy-sklad-deploy` (закрытый ключ) |
| `DEPLOY_SSH_KNOWN_HOSTS` | Вывод `ssh-keyscan -t ed25519 <IP>` — отпечаток сервера, чтобы GitHub не подключился к подменённому |

Перед `ssh-keyscan` один раз войдите сами: `ssh -i $HOME\.ssh\moy-sklad-deploy root@<IP>`. Если провайдер
показывает отпечаток ключа сервера в панели, сверьте его с тем, что спросит `ssh`.

## 4. Первый запуск

**Actions → moy-sklad deploy (production) → Run workflow**: в `confirm` введите `DEPLOY`, в `install_domain` —
ваш домен. Нажмите **Approve**, когда workflow попросит утверждение.

Workflow заново прогонит проверки, загрузит файлы на сервер, выполнит `install.sh` (10–20 минут) и применит
схему базы. В дальнейших запусках `install_domain` оставляйте пустым: будут применяться только новые миграции.

## 5. Владелец, пароли, сборка приложения

Зайдите на сервер (`ssh -i $HOME\.ssh\moy-sklad-deploy root@<IP>`) и выполните:

```bash
bash /opt/moy-sklad/deploy/create-owner.sh         # email, пароль, название компании
sh /opt/moy-sklad/supabase/run.sh secrets          # пароли сервера — в менеджер паролей, не в чат
grep '^ANON_KEY=' /opt/moy-sklad/supabase/.env     # публичный ключ для сборки приложения
```

Для сборки приложения в EAS задайте `EXPO_PUBLIC_SUPABASE_URL=https://<домен>` и
`EXPO_PUBLIC_SUPABASE_ANON_KEY=<ANON_KEY>`. Эти два значения публичные: доступ к данным ограничивают
правила RLS в базе.

Панель управления Supabase (Studio) открывается на `https://<домен>/` под логином и паролем
`DASHBOARD_USERNAME` / `DASHBOARD_PASSWORD` из `run.sh secrets`.

## Каждый день

- **Резервные копии**: в 03:30 по времени сервера, папка `/var/backups/moy-sklad`, 14 дней.
  Проверить: `systemctl list-timers moy-sklad-backup.timer` и `journalctl -u moy-sklad-backup -n 20`.
- **Копия вне сервера** — обязательно до начала работы: если сервер пропадёт, пропадут и копии на нём.
  Создайте бакет в объектном хранилище того же облака, настройте `rclone config` (удалённое хранилище
  S3 и поверх него `crypt`, чтобы копии лежали зашифрованными) и укажите его в `/etc/moy-sklad/backup.env`:
  `RCLONE_TARGET=имя-crypt-хранилища:moy-sklad`. Установка: `apt-get install -y rclone`.
- **Обновления безопасности Ubuntu** ставятся автоматически.
- **Обновление Supabase** — по официальной инструкции (`sh update.sh --dry-run`, затем `sh update.sh`),
  только после свежей копии. Делаем вместе.

## Восстановление из копии

В архиве лежат `db.dump` (база) и `supabase.env` (ключи). Без ключей из `supabase.env` восстановленная база
не подойдёт к приложению: старые входы перестанут работать. Порядок восстановления на новый сервер нужно
один раз отрепетировать на тестовом сервере до начала работы — `backup.sh` проверяет только, что копия
читается целиком.

## Ограничения

- Скрипты проверены без реального сервера: настройки Docker Compose — командой `docker compose config`
  на официальных файлах этой версии, `migrate.sh` — тестом на PostgreSQL 16 (`tests/db/deploy-migrate.test.js`).
  Первую установку стоит провести вместе.
- Письма (сброс пароля по email) не настроены: в официальной сборке стоит заглушка вместо почтового
  сервера. Пока пароли меняет владелец через Studio; почту (SMTP) подключим отдельно.
